# Structured Data and Entity Markup — Sitewide Developer Audit Instructions

**Scope:** Entire SearchSarkariNaukri project  
**Status:** Instructions prepared; findings require repository and site evidence.

## Complete checklist

## 11. Structured Data and Entity Markup

- [ ] Audit existing JSON-LD, Microdata, or RDFa before changing it.
- [ ] Select schema types based on actual page content and current supported guidelines.
- [ ] Consider `Organization`, `WebSite`, `BreadcrumbList`, and appropriate `Article` or `NewsArticle` markup where eligible.
- [ ] Use job-related structured data only if the page and vacancy genuinely meet the current requirements.
- [ ] Do not mark a general exam listing as a job posting merely to gain visibility.
- [ ] Populate properties from verified page data.
- [ ] Keep structured data consistent with visible content.
- [ ] Use accurate canonical page URLs and entity identifiers.
- [ ] Avoid fake ratings, reviews, author credentials, dates, salaries, or availability.
- [ ] Avoid duplicate conflicting schema generated by multiple components.
- [ ] Validate representative pages using current schema validation tools.
- [ ] Monitor Search Console enhancements and structured-data warnings where available.

## Detailed developer instructions

Inventory JSON-LD/Microdata/RDFa before changes. Use types that match visible eligible content. Compare properties with page facts/canonicals, identify duplicate schema, validate representative templates and record tool output. Never add fabricated jobs, dates, salary, ratings or availability.

## Pass 1 — Audit and implementation

- [ ] Inspect current code/data and capture reproducible baseline evidence.
- [ ] Identify affected routes/components; preserve useful content, records, URLs and working behavior.
- [ ] Record confirmed findings and distinguish evidence from assumptions.
- [ ] Assign priority; document fix, expected result, dependencies and approvals.
- [ ] Implement only scoped approved changes using project conventions.
- [ ] Run applicable local checks; record exact commands/results.
- [ ] Record changed files/components and unresolved items.

## Pass 2 — Independent verification

- [ ] Recheck the original issue against rendered routes or actual system behavior.
- [ ] Verify content/data preservation and applicable metadata, schema and links.
- [ ] Exercise desktop/mobile, keyboard and relevant loading/empty/error/success states.
- [ ] Inspect relevant console/network output and regression paths.
- [ ] Attach reproducible evidence; mark passed, failed, blocked or untested.
- [ ] Keep unresolved items open; code changes or a passing build alone do not prove success.
